## 1. 结论先行

| 决策 | 结论 |
|---|---|
| 主语言/运行时 | TypeScript（ESM）+ Node ≥ 22 LTS |
| 插件底座 | **cordis**（npm 锁版，不 vendor；dsh 的做法是 vendor 以完全掌控框架层，我们规模未到，锁 rc 版本起步） |

## 2. 参照系调研摘要（证据在 research/deepseek-harness/）

### 2.1 cordis 用法（"Everything is a Plugin"）

- 宿主 `boot()` 只做四件事：`new Context()` → `ctx.plugin(Loader)` → 挂根 Include → 等整棵插件树 settle（`packages/boot/app-boot/src/index.ts`）
- 之后**一切功能都是配置树里的插件行**：`packages/bundle/base/cordis.patch.yml` 把 timer、hmr、llm、plugin-manager、web-app、config-editor 全声明为 entry
- 插件两种形态：函数式（`export name + Config + apply(ctx, config)`）与类式（`default export class` + `static inject` + `static Config` + `async* [Service.init]()` 生成器 yield 清理逻辑）
- DI 三件套：`@Inject('loader')` 装饰器 / `ctx.inject([...], cb)` 作用域回调 / `Service` 基类 + `declare module` 往 Context 上合并服务接口
- 配置：插件用 schemastery 声明 schema；运行时配置本体是 Loader 的 YAML entry 树 + patch 方言
- HMR、插件市场、npm 安装管理等全都有完整实现（`packages/boot/hmr/`、`plugin-manager/`、`plugin-market/`）
- 理论文档：cordis《A Programming Paradigm for Spatiotemporal Composability》(arXiv:2608.25512)
- 同领域先例：Koishi（cordis 作者的聊天机器人框架，adapter/plugin/console webui 三层同构）——先例证明这条路在我们的领域成立，但我们不 fork 它

### 2.2 WebUI 架构

- React 18 + Vite；`apps/web` 只是薄壳，功能代码在 `packages/client/ui-*` 几十个包
- **不是路由注册，是 Slot 注册中心**：`packages/client/ui-slots` 的 `SlotMap`（declaration merging 声明插槽契约）+ `ctx.slots.register({name, id, order, label}, Component)`
- 布局由 `ui-layout` 的 `LayoutController` 切换 `'main'` keyed 插槽里的面板；侧边栏/右栏/底栏/浮层都是插槽
- **同包双入口**：`src/index.ts`（宿主半边）+ `src/client/index.ts`（浏览器半边），浏览器端有自己的微型 cordis 运行时（`__ModuleLoader__` 按 manifest 懒加载）
- 前后端通信：`/connect` 令牌握手 → 类型化 RPC over WebSocket（Typert 代码生成 `ctx.remote.*` + zod 线格式校验）
- 双 tsconfig program（host/client 分开类型检查，同一 Context 键在两侧合并不同服务）

### 2.3 .agents 开发管理体系

- `CLAUDE.md` 是指向 `AGENTS.md` 的 **symlink**（单一事实源）；`.claude/skills` symlink 到 `.agents/skills`——工具中立
- `.agents/notes/`：agent 写的 ADR 体系，`{proposed|implemented|rejected}/{feature|architecture|process|…}/yyyy-mm-dd-topic.md`，强制 `Status` 头 + `Problem`/`Alternatives considered` 骨架，格式有脚本门禁
- `.agents/skills/`：22 个项目专属技能（pre-push-checks、code-review、doc、prose-standard…）
- 根 `AGENTS.md` 只放命令与规约（词数上限由脚本强制）；知识分层 "one home per fact"：AGENTS.md=命令 / architecture.md=地图 / 子系统文档=类型 / agent notes=决策理由 / cookbook=操作步骤 / 包 README=契约
- lefthook 本地门禁只做窄检查（staged lint、空白符、冻结文件），全量矩阵归 CI

## 3. 核心设计：双层插件模型

dsh 的"一切皆插件"直接照搬会和需求里的"业务插件"撞概念。明确分两层：

```
┌─ 系统插件（cordis plugin，平台自身能力，运维/开发装配）
│   channel-feishu / webserver / store / queue-worker / dispatcher / webui-* / auth …
│
└─ 业务插件（bot plugin，面向统一事件，管理台装配）
    help / echo / order-query …
    本质 = 一个 cordis 插件，向 botPlugins 服务注册自己，
    由 dispatcher 按 DB 里的挂载顺序串行调度
```

| 维度 | 系统插件 | 业务插件 |
|---|---|---|
| 装配方式 | 启动配置（YAML entry 树，借鉴 loader） | 管理台挂载到机器人（存 DB） |
| 面向对象 | 平台内部服务（DI、Service） | 统一事件模型 |
| 顺序 | 启动依赖（inject 声明） | 用户排序（DB `mounts.order`） |
| 约束 | 无能力校验 | **能力协商**：`required_capabilities ⊆ bot.capabilities` |
| 生命周期 | cordis 标准（fiber dispose/HMR） | 同左（挂载/卸载 = 注册表增删） |

业务插件标准形态（函数式，最贴近 cordis 习惯）：

```ts
// packages/plugins/help/src/index.ts —— 官方示例插件
import { Context } from 'cordis'
import { z } from 'schemastery'

export const name = 'help'
export const Config = z.object({ template: z.string().default('可用命令：…') })

export function apply(ctx: Context, config: { template: string }) {
  ctx.botPlugins.register({
    id: 'help',
    requiredCapabilities: ['im:message.reply'],
    async onEvent(event, runtime) {          // event 只读；runtime = { shared, reply, logger, signal }
      const text = event.message.content.text ?? ''
      if (!/^(帮助|help)/i.test(text.trim())) return 'next'
      await runtime.reply({ type: 'text', text: config.template })
      return 'handled'                        // 短路后续插件（ADR D4）
    },
  })
}
```

关键服务（都按 dsh 方式用 `Service` + `declare module` 合并到 Context）：

```ts
declare module 'cordis' {
  interface Context {
    botPlugins: BotPluginRegistry   // 业务插件注册表（声明 meta + onEvent）
    store: Store                    // 配置库 + 事务记录（SQLite 实现）
    dispatcher: Dispatcher          // 请求内同步执行：幂等/能力复核 → 责任链 → 事务落笔
    botReply: ReplyGateway          // 统一回复 API（ADR D5），翻译到渠道插件
  }
}
```

## 4. 配置双源（与 dsh 的关键差异）

dsh 是**配置文件中心**（YAML entry 树即一切）；我们的管理对象是运行时数据，管理台要 CRUD。因此：

| 源 | 管什么 | 形态 |
|---|---|---|
| YAML（loader entry 树） | 系统插件装配：启停哪些渠道适配、webui、存储后端、端口等 | `config/cordis.yml` + `cordis.patch.yml`，借鉴 dsh 方言 |
| SQLite | 域模型：回调服务、机器人、能力枚举、插件挂载关系（含顺序）、事务记录 | 管理台读写，dispatcher 执行前实时读 |

规则：**域模型永远不进 YAML，系统装配永远不进 DB**。一刀切清楚，避免两源打架。

## 5. Monorepo 布局

```
im-bot-router/
├── apps/
│   └── server/                  # 薄宿主：boot + loader + 默认 bundle（对标 apps/cli）
├── packages/
│   ├── core/                    # cordis-free 叶子包：统一事件模型、能力枚举、事务类型（对标 dsh 的 client-safe 包）
│   ├── channels/
│   │   └── feishu/              # P0 渠道适配：验签/AES 解密/challenge/归一化/回复翻译
│   ├── engine/                  # queue-worker + dispatcher（责任链、幂等、短路）
│   ├── store/                   # SQLite + Service 抽象（config & transaction 两域）
│   ├── plugins/                 # 官方业务插件：help、echo（示例与测试夹具）
│   └── client/
│       ├── web/                 # webui 壳（对标 packages/client/web）
│       ├── slots/               # 简化版 Slot 注册中心（SlotMap + register）
│       ├── ui-bots/             # 机器人管理页（含能力勾选、插件排序）
│       ├── ui-plugins/          # 插件清单页
│       ├── ui-transactions/     # 事务查询/详情页
│       └── ui-services/         # 回调服务管理页
├── docs/                        # 00 需求 / 01 本文档 / cookbook/…
├── .agents/{notes,skills}/      # §8
├── AGENTS.md                    # §8（CLAUDE.md 为 symlink）
├── lefthook.yml
└── pnpm-workspace.yaml
```

包名约定：`@im-bot-router/<group>-<name>`（对标 `@deepseek-ai/dsh-*`）。

## 6. WebUI 方案（Slot 简化版）

- React + Vite；`main` 为 keyed 插槽，四个管理页各自注册；侧边栏为 single 插槽
- 每个页面组件在**浏览器半边**的 `apply(ctx)` 里 `ctx.slots.register({ name: 'main', id: 'bots', order: 20, label: '机器人' }, BotsPanel)`
- 通信 v1 不上 Typert 代码生成：HTTP API + zod 请求/响应校验，客户端统一 `ctx.remote.*` 门面（接口形状与 dsh 对齐，将来平滑升级 WS）
- 浏览器端跑 cordis（同 dsh 的双运行时思路），但 v1 允许整包静态构建（不做 `__ModuleLoader__` 懒加载，P1 再拆）

```ts
// packages/client/ui-bots/src/client/index.ts
export const inject = ['slots', 'remote']
export function apply(ctx: Context) {
  ctx.slots.register({ name: 'main', id: 'bots', order: 20, label: '机器人' }, BotsPanel)
}
```

## 8. 开发管理体系（直接采纳 dsh 范式）

- **AGENTS.md**：单一事实源，只放命令与规约；`CLAUDE.md` symlink 过去；按需在子树（packages/、docs/）加局部 AGENTS.md
- **`.agents/notes/`**：ADR 体系，v1 简化版——路径 `{proposed|implemented|rejected}/{architecture|feature|process|bug-fix}/yyyy-mm-dd-<slug>.md`，头两行 `# Agent Note: <title>` + `Status: <lifecycle> — <why>`，必有 `## Problem` / `## Alternatives considered`。**不做** i18n 三件套与冻结哈希门禁（P1 再上格式校验脚本）
- **`.agents/skills/`**：随项目长出专属技能（第一个：`bot-plugin-dev`——写业务插件的操作手册）
- **lefthook**：pre-commit 窄检查（staged lint + 尾随空白），pre-push typecheck；全量归 CI
- **知识分层**："one home per fact"——docs/00 需求 / docs/01 技术方案 / docs/cookbook 步骤 / agent notes 决策理由 / 包 README 契约；每层设词数预算（v1 手工约束，P1 上 `verify-doc-budgets`）

## 9. 借鉴清单：采纳 / 简化 / 不做

| dsh 机制 | 处置 | 理由 |
|---|---|---|
| cordis 底座 + Service/DI/生命周期 | **采纳** | 本方案的骨架 |
| Everything is a Plugin（含 webui、配置编辑器皆插件） | **采纳（双层模型改造）** | 防止与业务插件撞概念 |
| Loader YAML entry 树 + patch 方言 | **简化采纳** | 只管系统插件装配；域模型进 DB（§4） |
| Slot 插槽 UI 注册 | **简化采纳** | 去掉 5 种 kind 中的 chain/hoc，v1 只要 single/keyed |
| Typert 类型化 RPC 代码生成 | **不做（v1）** | 手写 zod + HTTP 门面够用，接口形状对齐便于日后升级 |
| vendor cordis | **不做（v1）** | npm 锁 rc 版；升级受制于人时再考虑（风险见 §10） |
| plugin-manager（pnpm 动态安装）+ plugin-market | **不做（v1）** | v1 插件 = workspace 包 + 管理台发现；市场无需求 |
| HMR | **不做（v1）** | dev 重启够快；上量后再挂 cordis 官方 hmr |
| .agents/notes + skills + symlink 体系 + lefthook + doc tiering | **采纳（简化）** | 项目从第一天就是 agent 参与开发，这套范式正合适 |
| per-file 100% 覆盖率门禁 | **不做** | 中间件/胶水层为主的仓库，盲目 100% 得不偿失 |

## 10. 风险与不确定项

1. **cordis 处于 4.x rc**：API 可能破坏性变更（dsh 因此 vendor + 自写升级计划）。缓解：锁精确版本、core 包隔离 cordis 类型依赖（参照 dsh 的 cordis-free 叶子包策略）、升级走 agent note 记录
2. **dsh 本身 developer preview**："THERE WILL BE COMPATIBILITY-BREAKING CHANGES"——我们借鉴的是**范式**而非直接依赖它的包，不受其破坏性变更影响
3. **浏览器端 cordis 双运行时**复杂度：v1 允许客户端退化为普通 React 应用 + 唯一插件入口（渐进到全插件化），不算阻塞
4. **文档获取**：cordis 官网/docs 若被墙走 7890 代理或读 dsh vendor 源码（`research/deepseek-harness/vendor/cordis/` 就是可读的 cordis 全源码，这是 clone 的额外价值）
5. **飞书凭证**：P0 验收需要一个真实飞书测试应用（app_id/secret + 事件订阅权限），需要你提供或在飞书开放平台自建
